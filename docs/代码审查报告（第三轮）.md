## 一、本轮新发现 —— P0 必须修

### P0-1 拼团：容量无原子扣减可超卖；团失败后迟到付款仍按拼团价入账（资损）

- 参团容量检查在事务外（`server/internal/service/groupbuy.go:97-104` 普通 COUNT），事务内无复检，`uk_gbm_group_user` 只防同一人重复——剩 1 席时 N 个不同用户并发 Join 全部成功，**超员者照常按拼团价支付入账**。对照同文件 `claimActivity`（`groupbuy_activity.go:32-44`）已有正确的条件 UPDATE 范式。
- 更重的资损路径：`CloseGroupBuys`（`task/task.go:284-336`）置团 failed 并对当时已 paid 订单自动退款后，遗留的 pending 订单 2 小时内仍可 prepay；`HandlePaySuccess` 不校验拼团状态、无条件入账（`order.go:719,731-734`）——**自动退款已跑完，用户以拼团价拿到课包且永不退差价**。
- 修法：① Join/Open 事务内对 group_buy 行条件 UPDATE 占席（校验 status=enrolling、未过期、已占数 < capacity），或 `SELECT ... FOR UPDATE`；② `creditSessions` 前对 `group_buy_id > 0` 的订单校验团状态，非 enrolling/success 的迟到付款走自动退款而非入账。

### P0-2 老账户 unit_price=0 残留 → 退款按 0 元折算（资损）

- 00005 的回填（`migrations/00005_review_fixes.sql:18-21`）`JOIN package_sku` 覆盖不到**物理删除过 SKU 的老账户**（M5 修复前后台编辑即物理删行），这些账户 unit_price 恒 0；`calcRefundAmount` remainder 分支 `amount = remaining × 0 = 0`（`service/order.go:451`）。
- 真实通道：微信拒 0 元退款 → 退款单永久卡 approved、订单卡 refunding（课时已被回收）；mock 通道：`QueryRefund` 恒 SUCCESS → finalize 以 amount=0 把订单置 refunded——**课时没了、一分钱没退**。
- 修法：`calcRefundAmount` 中 `mp.UnitPrice <= 0` 时回退订单快照 `order.SkuUnitPrice`；仍 ≤0 或最终 amount≤0 时走 `errs.Biz` 拒绝分支（现有补偿逻辑能把订单退回 paid）。

### P0-3 教练端"学员反馈"页空指针崩溃（功能不可用）

- `service/feedback.go:146` `fb := s.OfVerification(...)` 在无反馈时返回 nil（`feedback.go:73`），`:150` 直接 `fb.Content` 解引用 → panic → 500。列表中只要存在一条**未写反馈**的核销记录（这正是该页核心场景）必崩。已挂路由 `handler/feedback.go:44`，无测试覆盖。
- 修法：`fb == nil` 时输出空对象（`content:""`、`createdAt:null`）。

### P0-4 原生小程序首页残留 mock 登录 UI + 默认 debug 全 mock 配置（刷号刷钱）

- `miniprogram/pages/index/index.wxml:53-58`"开发：指定 mock 身份登录"卡片的显示条件仅是 `{{!user}}`——**任何未登录的真实用户都会看到**，输入 `mock-coach-1` 即可发 `POST /auth/login`；`wechat.mock=true` 时 code 即 openid（`wechat/miniapp.go:198-207`），可无限造新号，而新用户自动发新人礼包（`router.go:52-54`）+ 领券 = **直接刷钱**。
- 默认 `server/configs/config.yaml` 就是 `mode: debug` + 三个 mock 全开（`config.yaml:14-19,27,38,53`），release 校验只在 `mode=release` 时生效。
- 修法：删除原生小程序首页 mock 登录 UI 及 `index.js` 对应分支；上线 checklist 强制 `mode=release`；考虑 mode 默认改为 release、debug 启动打醒目告警（见 P1-10）。

## 三、P1 建议改（按主题分组）

### 3.1 退款/关单链路的孤儿态（本节与 P0-2 同为接真实支付前必修）

1. **支付回调与超时关单竞态：已付款订单无痕消失**——用户把收银台挂超 2 小时后付款，回调事务读单时 pending、关单任务恰在此刻提交，条件 UPDATE 命中 0 行后直接 `return nil` 并向微信应答 SUCCESS（`order.go:702-704`）——钱已扣、订单 closed、**无 failed 留痕、无日志、无入账**，微信也不再重试。修法：RowsAffected==0 时回读订单，closed 则 markPaymentFailed+告警。
2. **ApproveRefund 闸门后任何一步失败 → 永久孤儿 approved**——审批事务内并发消耗课时返回 Conflict 时闸门已 approved（`order.go:478-483` vs `:540`），管理员按提示"重新审批"被闸门挡死；轮询只对 `r.Amount > 0` 重发（`:593`），amount=0 的单**永久卡死只能改库**。修法：闸门与结算合并进同一事务，或轮询识别 amount=0 的 approved 单回退 pending。
3. **RejectRefund 两条语句非事务、错误吞掉**——退款单置 rejected 后订单回 paid 的 UPDATE 不查 `.Error`（`order.go:650-658`），中途失败订单永久 refunding 且无活跃退款单、无扫描任务。修法：合并事务；补"refunding 无活跃退款单"修复扫描。
4. **退款 ABNORMAL/CLOSED 终态无人处理**——轮询对非 SUCCESS 一律保持 approved 下轮重试（`order.go:588-607`），微信余额不足将永久轮询：课时已回收、钱未退。修法：连续 N 次 ABNORMAL/CLOSED 置 refund.status=failed（常量已定义未使用）+ 告警 + 订单回 paid 并返还课时，转人工。

### 3.2 权限与部署

5. **课包/规格保存未挂 RequireBoss**——第二轮角色守卫修复覆盖了退款/调课/配置/券/活动/入驻，但 `router/router.go:237-238` 课包/规格保存（含改价）漏挂，receptionist 仍可改价。修法：补 `RequireBoss()`。
6. **默认管理员口令残留**——release 校验已强制 `ADMIN_INIT_PASSWORD`（config 层），但 `BootstrapAdmin` 未设密码时仍回落 `fitness123`（`service/auth.go:343`），且 `admin-web/src/views/Login.vue:16` 把默认口令**明文写进登录页随生产构建发布**（readme.md:32、docs/本地启动指南.md:51 同样在库内）。修法：删 Login.vue 提示行；BootstrapAdmin 无密码时拒绝而非回落。
7. **debug 模式误上线即全失守**——全部 mock 通道与弱口令仅在 `mode=release` 时被拦截，debug 模式无任何强制告警（`config.go:166-193`）。修法：mode 默认 release；debug 启动打醒目告警；生产部署 checklist 增加"启动日志核对"。
8. **时区强约束未固化**——booking_date/任务扫描/活动窗口全部用服务器 `time.Local` 与字符串日期比较（`booking.go:68,214`、`task.go:207,218,263`），服务器时区≠Asia/Shanghai 时"今天"边界整体偏移 8 小时。代码内部自洽，但建议启动时 `time.LoadLocation("Asia/Shanghai")` 显式固定并写进部署文档。
9. **00006 对存量重复手机号会启动失败**——存量存在相同非空 phone 时 `ADD UNIQUE INDEX` 报 1062（不在迁移容错清单）→ 服务无法启动。上线前先跑去重检查，或迁移内先合并/置 NULL。
10. **orders.group_buy_id 无索引**——`paidCount`/`Detail`/`autoRefundGroup` 均按其查询（`groupbuy.go:312-314,344-346`）。补 `KEY idx_order_groupbuy (group_buy_id)`。

### 3.3 滥用防护（接真实短信通道前必修）

11. **短信频控 TOCTOU + 无验证码 + 无全局配额**——60s 重发与单日 5 条均为先查后插（`auth.go:137-158,204-210`），并发可穿透；验证码 attempts 自增不带 `attempts < 5` 条件；无图形验证码、无全局小时级熔断。接通真实服务商后 = 短信费资损。修法：日限原子化（(phone,date) 条件 INSERT/计数）；attempts 条件更新判 RowsAffected；接入验证码与全局熔断。
12. **上传接口无限流、无用户配额**——`/api/v1/uploads` 仅 RequireUser（`router/router.go:156`），任一登录用户可多线程上传 2MB 合法图片写满磁盘。修法：挂 LoginRateLimit + 每用户日配额。（文件类型魔数校验、随机文件名、无路径穿越——这部分做得对。）
13. **下单/prepay 无频控**——可刷 pending 单膨胀库表（`router.go:127-131`）；`genOrderNo` 撞 `uk_order_no` 不重试（`order.go:46-50`）。

### 3.4 支付与联动

14. **支付回调纵深**——未断言 `transaction.Mchid/Appid` 与配置一致；`paidAmount > 0` 才比对金额，回调缺 amount 字段时放行入账（`handler/pay.go:35-57`、`order.go:677`）。当前有平台证书验签兜底，属必须补的闸门。
15. **支付成功事务外联动丢失窗口**——HandlePaySuccess 提交后、`RewardOnPaidOrder`/`OnOrderPaid` 前崩溃：老带新奖励永不发（无补偿扫描）；拼团单付了款但 TrySucceed 未跑，恰逢到期会被 `CloseGroupBuys` 把**实际已满员的团置 failed 全员退款**（`order.go:727-734`、`task.go:284-306`）。修法：task 增加近期 paid 订单联动补偿扫描；CloseGroupBuys 置 failed 前先查 `paidCount >= capacity` 走 TrySucceed。

### 3.5 其他正确性

16. **CancelByCoach 部分失败后不可重试**——先把团置 cancelled 再逐人返还，某学员失败仅计数（`group.go:471-507`），提示"重试取消"但重试被 cancelled 闸门拒绝 → 该学员课时被吞。返还幂等键已安全，应允许对 cancelled 团重入补返还。
17. **deductOne"首扣开卡"忽略 `.Error`**（`booking.go:301-307`）——失败则账户停为 inactive 且无有效期，静默带病运行。
18. **coachapply 审核闸门与建档非同事务**（`coachapply.go:159-174`）——upsert 失败 → approved 但无教练档案且无法重审；中文名长度校验用字节 `len()` 与其他模块 rune 不一致。
19. **profile 头像域校验可绕过**——`strings.Contains(url, "/uploads/")`，`https://evil.com/?x=/uploads/` 可注入外链头像（`profile.go:24`）；coachapply 的 `HasPrefix` 写法是对的，应统一。

### 3.6 前端

20. **推荐绑定失败被永久屏蔽（双端同 bug）**——`client/src/utils/referral.js:30-33`、`miniprogram/utils/referral.js:20-23` 在 `finally` 里无条件清除 pendingInviter 并置 referralBound=1——一次网络抖动就永远失去绑定机会（首单得券、老带新奖励直接丢）。修法：仅成功或服务端明确"不可绑定"时置位。
21. **JWT 30 天 + 登出无服务端吊销**（对应 L4）——token 本地明文存储（三端均是），泄露后最长 30 天无法作废。修法：短 access token + refresh，或 token_version。
22. 小程序 `project.config.json` `urlCheck:false` + API 地址 `http://127.0.0.1:8080`（`app.js:7`、`client/src/utils/config.js:7`）——上线忘改即失联或明文。构建脚本强制校验。
