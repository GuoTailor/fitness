## 二、本轮新发现 —— P0 必须修

### P0-1 管理后台角色分离失效：RequireBoss 零引用

- `middleware/auth.go:127-137` 的 `RequireBoss` 全仓库无任何路由引用；`router/router.go:128-168` 全部 admin 路由仅挂 `RequireAdmin()`。
- 后果：receptionist（`model/user.go:55` 默认角色）可调用**退款审批**（`handler/admin_order.go:105`，真实打款）、**手动增减学员课时**（`admin_order.go:163`）、**改课包价格**（`admin_shop.go:110`）、改运营配置。
- 修法：签发 token 时把 `AdminUser.Role` 写进 claims；退款审批、课时调整、配置修改挂 `RequireBoss()`；同时修掉 `Username==""` 判角色的旧逻辑。

### P0-2 退款审批顺序倒置：先打款、后抢闸门

- `service/order.go:195` 先调 `pay.Refund`（真实发起微信退款）→ `order.go:200-205` 才做 `pending→approved` 状态闸门 → `order.go:207-240` 才落库回收课时。
- 攻击/出错场景：
  - 管理员 A 点同意（阻塞在微信网络调用），管理员 B 同时点拒绝——B 的 `pending→rejected` 抢先成功、订单回 paid（`order.go:255-264`）；A 从微信返回后闸门失败报"已被处理"。终态：**微信侧钱已退，本地 refund=rejected、order=paid、课时未回收**。
  - 闸门成功后、事务前进程崩溃 → approved 孤儿态，重试被 `order.go:204` 挡死，课时永不回收。
- 修法：调换顺序——先条件 UPDATE 抢闸门（影响行数=0 即停止）→ 事务内落全部 DB 变更 → 再调微信退款，失败回写状态供重试；增加"approved 超 X 分钟未终态"的恢复扫描任务。

### P0-3 退款金额基于事务外旧读折算，且 refund.amount 从不落库

- `order.go:184` 在闸门/事务外读 member_package → `order.go:153-171` 按旧 remaining 折算 → `order.go:210-225` 事务内仍用旧值写流水。
- 后果：打款期间学员又核销 1 次 → 实际剩 4 仍按 5 退，**商家超退**；流水与余额对不上，对账失真。
- 同时 `order.go:200-202`、`:238-239` 两处 UPDATE 均未写 amount——**refund.amount 恒为 0**（`:244` 仅改内存对象），无法做"累计退款≤实付"校验与对账。
- 修法：闸门通过后在事务内 `SELECT ... FOR UPDATE` 重读重算并 cap（≤实付-已退）；先落 `amount` + 快照列，再发起微信退款。配套 DDL：

```sql
ALTER TABLE refund
  ADD COLUMN unit_price BIGINT NOT NULL DEFAULT 0 COMMENT '审批时快照：单课时折算价(分)',
  ADD COLUMN reclaimed_sessions INT NOT NULL DEFAULT 0 COMMENT '审批时快照：回收课时数',
  ADD COLUMN calc_type VARCHAR(16) NOT NULL DEFAULT '' COMMENT 'full/remainder/manual';
```

### P0-4 团课"退出后重报"账实不符（资金/账务级）

- 重报复用原 enrollment 行、ID 不变（`group.go:197-204`），而流水幂等键只含 enrollmentID：
  - 二次报名：`group.go:231` 键 `group_deduct:{enrollmentID}` 与首次流水撞唯一键，`booking.go:231` 对 duplicate 静默吞掉——**余额扣了 1 节，流水没记录**（违背"以流水为准对账"，`00001_init.sql:190`）。
  - 二次退出：`group.go:277` 键 `group_refund:{enrollmentID}` 撞键、`booking.go:247-249` 提前 return——**状态置 quit、名额释放，但课时没返还也没流水**，用户白丢 1 节课。
- 修法：

```sql
ALTER TABLE group_enrollment ADD COLUMN enroll_seq INT NOT NULL DEFAULT 1 COMMENT '报名世代：quit→enrolled 时 +1';
```

  Enroll 复用分支 `enroll_seq+1` 并回读，扣次/返还键改 `group_deduct:{enrollmentID}:{seq}` / `group_refund:{enrollmentID}:{seq}`；事务内对 enrollment 行 `SELECT ... FOR UPDATE` 防世代错乱。

### P0-5 IP 限流可被 X-Forwarded-For 绕过（防爆破失效）

- router 未调用 `SetTrustedProxies`（gin 默认信任所有代理）；`middleware/ratelimit.go:47-52` 实际用 `c.ClientIP()`。
- 后果：伪造 XFF 即可无限轮换"IP"，绕过登录限流与后台 `username@ip` 锁定。
- 修法：直连部署 `r.SetTrustedProxies(nil)`；nginx 部署显式配置可信网段；release 模式强制校验。

## 五、逻辑断链与孤儿状态（"只定义、无人写入"）

这批问题的共性：状态定义了、读取时也过滤了，但没有任何代码把状态写进去；定时任务（`task/task.go` 只有评价邀请 + 课时预警）未承担状态推进职责。**用户旅程正向链路（购买→支付→开卡→预约→核销→评价）是通的，反向与超时链路整体缺失。**

| 孤儿状态 | 定义处 | 后果 | 需要的机制 |
|---|---|---|---|
| 订单 closed | `model/order.go:9` | 挂单无限堆积；旧价订单可无限期支付 | 超时关单任务 + 迟到回调策略（见 M2） |
| 团课 closed/finished | `model/booking.go:71,73` | 过点团课永远显示"报名中/满员"，14 天日历历史课一直挂着；学员 myStatus 永远 enrolled | 结课任务：开课时间已过且未取消 → finished（有核销）/closed |
| 预约 expired | `model/booking.go:28,33`（注释声称释放 token，实际无人写） | no-show 课时永久占压、无流水出口、时段不释放、教练历史 pending 积压 | 过期任务 + 罚没/返还规则（`TxnTypePenalty` 同为死代码，`model/member.go:46`），需产品定规则 |
| 课包 expired | `model/member.go:10` | 过期课包可继续预约/团课/消费（见 M3） | 过期清扫任务 + 消费入口校验 expire_date |
| payment failed | — | 支付失败（CLOSED/PAYERROR）无任何记录，无法排查 | 回调对非 SUCCESS 落失败流水并考虑触发关单 |
| 退款单 approved→refunded 推进 | `order.go:233-239` | 退款单/订单口径分裂，对账与展示不一致 | 退款轮询任务或真实验签的退款回调（见 M4） |
| notify_log 失败后永久丢失 | `notify.go:37-44`（先落库后发送）、`:59-65`（markFail 不清键） | 同 (user,scene,biz) 撞唯一键永远不再发送；定时任务型通知失败的那次正是唯一触达机会 | markFail 时删除该行（释放键位）或允许对 status=fail 行重发；任务侧重扫失败条目 |
